P33|Introduction
P34|The Department of Stamps and Registration (henceforth referred to as “department”) is the custodian of registered public records such as Registration of Marriages and Firms, Documents about transactions namely sale, transfer or gift of immovable properties, Mortgage, Power of Attorneys, wills and many more. Maintenance and preservation of these critical public records is the prime responsibility of the department. The records or the information associated with registered records are to be made available to the public when requested through defined procedures. The department is also responsible for collecting stamp duty on behalf of the Government for specified transactions. The services are provided through 260 Sub-Registrar Offices (SROs), under the supervision of 35 District Registrar Offices, spread across the state.
P35|The department has computerized the delivery of these services through the development of the Kaveri software. KAVERI Online service is a web-based application of the department that provides an interface to the Applicants required for documents, marriage, and firm registration. It enables Applicants to know the details of stamp duty, property guidelines, value, data entry for document registration and marriage registration, etc. The list of modules of Kaveri 2.0 is available in Annexure 1.
P37|About User Management
P38|The user management module of KAVERI 2.0 allows administrators to manage user accounts linked to the application. It typically provides functionality to create, edit, delete, and search for user accounts, as well as manage user roles, permissions, and access control.
P39|This module helps administrators to efficiently manage large numbers of users and assign appropriate permissions to each user.
P40|Some common features of a user management module include user authentication and activation, office creation and management of the roles, and post management. Overall, the user management module is a critical component of Kaveri 2 applications and helps ensure the security and integrity of user data and resources.
P42|Document scope
P43|This document defines the functional scope of the User Management Module for the KAVERI 2.0 application. This module is a foundational security and administrative component designed to allow authorised administrators – Super admin (DIGR admin), DRO admin and SRO admin to manage user identities, control access to application resources, and maintain the integrity of the system through structured role-based access control (RBAC).
P44|The document was prepared through document analysis and departmental consultation. The department shared the high-level requirements (Annexure 2).
P46|Definitions
P47|A Post is a specific, sanctioned position within the organisational hierarchy of the department, independent of the individual currently holding it. It has a designated grade and a formal job description. An officer is formally appointed to a Post.
P48|A Role is a defined set of responsibilities, permissions, and access rights within the Kaveri 2.0 system, assigned based on an officer's designated functions. It dictates what actions a user can perform and what data they can view.
P49|A User is an individual (typically a government officer or Contract employee) who has been given a unique identity to log in and interact with the Kaveri 2.0 system. A user is always associated with a specific Role to define their system
P50|To understand how these three concepts, work together, think of it this way:
P51|The authorities create a Post (e.g., DIGR) with a specific job description.
P52|An officer is appointed to fill that Post. This officer is now a User of the Kaveri 2.0 system.
P53|The system grants that User a specific Role (e.g., "DIGR_ADMIN", "DIGR_LAW") which gives them the digital permissions to perform the duties of their Post.

P414|Password Expiry Alert & Forced Change
P415|This process ensures system security by notifying users of password expiration and enforcing a mandatory password change upon expiry, in compliance with the organisation's password policy.
P416|Step-by-Step Process Flow
P417|Pre-Expiry Notification (X Days Prior)
P418|Trigger: System checks user password expiration date daily via automated background job.
P419|Action: If the password is set to expire in exactly X days, the system:
P420|Displays a prominent alert/warning message upon user login.
P421|(Alert message: "Your password will expire in [X] days. Please change it soon to avoid login interruption.")
P422|The user can either:
P423|Proceed to dashboard (alert remains dismissible but reappears on next login).
P424|Click "Change Now" to be redirected to the password change screen.
P425|Final Notification (1 Day Prior)
P426|Trigger: Password expires in 1 day.
P427|Acton: System displays a stronger warning:
P428|(Alert message: "Your password expires TOMORROW. Change it now to maintain access.")
P429|Change Password" button prominently displayed.
P430|Alert cannot be permanently dismissed until the password is changed.
P431|Expiry Day – Forced Password Change
P432|Trigger: Current date = password expiration date.
P433|Action: Upon login attempt:
P434|User is automatically redirected to the Password Change Screen.
P435|No access to any other system modules or dashboard.
P436|Screen displays: "Your password has expired. Please set a new password to continue."

P438|User enters:
P439|Current Password (for verification)
P440|New Password
P441|Confirm New Password

P443|Minimum length (e.g., 8 characters)

P445|Post-Change Actions

P458|Input and Output Descriptions
P459|Input validations
P460|Master Creation (Offices, Posts, User Types)
P461|Uniqueness Check: The system must prevent duplicate Office or Post names (e.g., you shouldn't be able to create two "DRO" office types).
P462|Dependency Protection: Prevent the deletion of a "Post Type" if there are active users currently assigned to it.
P463|Character Constraints: Ensure codes (like IGRO or SRO) follow a standard format (e.g., all caps, no special characters).
P464|User Creation
P465|The "One Person, One ID" Rule: Validate unique identifiers like Employee ID or Email to prevent duplicate profiles.
P466|Mandatory Mapping: A user cannot be saved without being linked to a valid Office Type (from Table 01) and Post Type (from Table 02).
P467|Format Validation: Ensure phone numbers and emails follow standard patterns (e.g., name@domain.com).
P468|Leave, Deputation, and Management
P469|Overlap Prevention:
P470|An employee cannot be on "Leave" and "Deputation" at the same time.
P471|A single post cannot be assigned to multiple users.
P472|Transfers and Promotions
P473|Active Status Check: You can’t transfer or promote a user who is currently marked as "Inactive".
P474|Post Availability: If a specific Office (e.g., SRO) only has 2 "DEO" slots, the system should warn the admin if a 3rd person is being transferred there.
P475|Effective Date Validation: Future-dated transfers should be allowed, but the system should only update the user's active permissions on that specific date.

P605|As-Is Process Description
P606|In the As-Is state, the KAVERI 2.0 User Management master data defines a fixed set of roles under each office type — SRO, DRO, and IGRO — without an SSR (Senior Sub Registrar) role anywhere in the hierarchy.
P607|Under this structure, a user attached to an SRO can only be mapped to SDA, FDA, or SR.
P608|A user attached to a DRO can be mapped to SDA, FDA, SR, HQA, DR, or DIGR.
P609|A user attached to an IGRO can be mapped to SR, HQA, AIGR, or DIGR.
P610|Because there is no SSR role, any officer who has grown beyond SR has to be elevated directly to HQA, which creates a wide responsibility gap between SR and HQA.
P611|To-Be Process Description
P612|In the To-Be state, a new role, SSR (Senior Sub Registrar), is introduced into the Master Data of the User Management module. SSR is added under all office types —Sub Registrar Office (SRO) District Registrar Office (DRO) and Inspector General of Registration Office (IGRO).
P613|Functionally, the addition of SSR requires the following changes in the User Management master data configuration:
P614|The Role Master must be updated to add "SSR" as a new selectable role value.
P615|The Office Type – Role mapping configuration must be updated so that SSR appears as an eligible role when the selected Office Types are SRO, DRO or IGRO.
P616|The role hierarchy sequence used for Add User, Promotion, and Role-based access control must be updated to position SSR between SR and HQA under SRO, DRO and IGRO.
P617|Existing role-mapping validations (e.g., role dropdown filtering by office type on the Add User / Edit User screens) must be revalidated to ensure SSR is added for all office types.
P618|Reports and MIS dashboards that consume role master data (e.g., user counts by role/office) must be updated to recognise SSR as a distinct, reportable role.
P619|With this change, the administrative hierarchy under SRO now reads SDA → FDA → SR → SSR, DRO now reads SDA → FDA → SR → SSR → HQA → DR → DIGR, and under IGRO it reads SR → SSR → HQA → AIGR → DIGR. This inserts an intermediate senior operational grade before an officer is elevated to the headquarters-level HQA role, aligning the system's role hierarchy with the Department's actual cadre structure.
