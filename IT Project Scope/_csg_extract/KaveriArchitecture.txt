Kaveri Architecture
1. About Kaveri
Kaveri is a digital platform designed to support end-to-end transactions of the registration
process, involving both citizen-facing and internal departmental workflows. It serves as the
primary interface for users through a web-based UI and coordinates multiple backend
capabilities such as identity management, reporting, and integrations with external government
and third-party systems.
The system has been live in production for over two years and currently operates with minimal
manual intervention. The primary architectural objective during the current phase has been
stability , operational predictability , and maintainability , rather than large-scale redesign.
2. Architecture Style and Principles
The system follows a service-oriented architecture  with the following characteristics:
Multiple independently deployed backend services implemented using .NET  Core (dotnet
8), python, golang.
A single-page web application built with Angular (v13) acting as the primary user interface.
A shared PostgreSQL  database instance used by multiple services.
Synchronous HTTP-based communication as the dominant interaction pattern.
Limited use of asynchronous processing for background and batch workloads.
Kaveri has two interfaces, citizen and department facing interfaces. The architecture and
deployments of both the interfaces are quite similar , with the only deviation being that the
department interface is exposed only KSW AN network and with some additional business
logic which is relevant only for the departmental workflows and should not be exposed to
the citizen interface.

UI Layer
Angular-based single-page application.
Handles user interaction, client-side validation, and orchestration of backend calls.
Closely coupled to backend API contracts.
Service Layer
Services responsible for business logic and workflow enforcement.
APIs exposed for UI and internal and/ or external consumption.
Data access implemented using Npgsql with Dapper.
Business rules enforced at the service level.
While most business logic is in dotnet, some functionalities are in python and
golang.
Data Layer
PostgreSQL  database shared across services.
Tables logically grouped by domain i.e. document registration, marriage registration, e-
Stamp etc.
Indexing and performance tuning applied based on production usage patterns.
Cache Layer
Redis instance for session and user management.
Response caching at both proxy and gateway level for quicker response without
compromise on quality of data.
Integrations
External systems accessed via synchronous APIs or scheduled jobs.
Integration logic encapsulated within dedicated service components where possible.
Data ownership is at the application level.

8. Known limitations
8.1 Shared Database Across Services
Multiple services access the same database instance, this is owing to the historical
implementation decisions. This can be mitigated, to a certain degree, by defining logical
boundaries for the data ownership.
8.2 Legacy Database Schema
Some domain logic including the database schema have been carried forward from Kaveri 1.
This is owing to early delivery constraints, backward compatibility requirements and evolving
understanding of the domain. Any change to these must account for all the dependencies and
accompanied by a thorough impact analysis.
8.3 Synchronous Service-to-Service Calls
Most inter-service communication is synchronous in nature, as it is simpler to manage. The
async orchestration might hurt latency sensitive workflows in the application. Latency analysis
is a must when further nesting service calls inside these services.The system must operate within state infrastructure (SDC) and compliance requirements.
Database separation is constrained by dependencies and operational risk.
Downtime tolerance is low for user-facing workflows.
Architectural changes must prioritize backward compatibility and rollback capability .
These constraints are considered non-negotiable unless explicitly revisited and approved.
